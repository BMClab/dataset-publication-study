# How PPDS chose its storage, query engine and toolkit

A researcher should be able to select older participants, find their walking trials, and compute a force summary from a versioned Zenodo deposit. A colleague with a local download should be able to repeat the analysis. PPDS also has users who want a single pressure frame or one foot mesh. The lab targeted whole datasets of roughly 10 MB to 1 GB and required an installable Python interface compatible with its marimo notebooks. Reuse from other languages and a small number of files were preferences. [Original requirements](../../evidence/reports/reader_benchmark_plan.md) · [Detailed selection record](selection-record.md)

## Which files and which reader?

The first experiments used a snapshot with 319 gait reports. HDF5 and Zarr ZIP supported selective array reads. Lance offered multimodal and object-store access, but the team could not verify a complete native Lance table query on a suitable Zenodo fixture. A SQLite web VFS received HTTP 403 on the tested endpoint. PyArrow and pandas provided useful reference and range-reading paths. Polars was the early preference for Parquet analysis because local selections were fast and its native and SQL interfaces agreed on the tested values. [Storage screening](../../evidence/reports/storage_benchmark.md) · [Reader comparison](../../evidence/reports/reader_benchmark.md) · [Public fixture checks](../../evidence/reports/zenodo_access_tests.md)

In the final comparison, four encodings represented the same eight tables, with 322 spatiotemporal reports and 190 meshes. The lab checked ordered values and mesh bytes after normalizing types. Some conversions lost schema annotations, so units and axes also needed a release dictionary. Parquet occupied 389.94 MB, compact Vortex 400.89 MB and native DuckDB 599.01 MB. Native DuckDB remained attractive for repeated local analysis. A single local Parquet trial took a median 12.2 ms with Polars and 54.7 ms with DuckDB in the five-repeat, evicted-page experiment. [Matched encodings](../../evidence/reports/lab_format_benchmark.md) · [Matched SSD experiment](../../evidence/reports/lab_formats_zenodo_ppds_local.md)

On a restricted Zenodo draft the lab measured what each reader actually transferred. Using DuckDB, the first single-trial query consumed 0.66 MB over 9 request attempts with Parquet and 18.20 MB over 7 with compact Vortex. Across all pressure observations, Parquet consumed 123.74 MB over 1,116 attempts and compact Vortex 72.73 MB over 25. These are decimal MB of upstream response bodies consumed by a counting relay, with one first observation per configuration. They illustrate how the frequency of selective and full reads can change the storage choice. [Hosted methods, failures and observations](../../evidence/reports/lab_formats_zenodo_ppds.md)

**Storage decision.** Parquet preserved values, supported existing independent readers and performed well for selective access. **Engine decision.** DuckDB SQL served the cohort joins, worked in Python and marimo, and let a second client reuse published SQL. The team exercised Python and Node.js. R and MATLAB support in the study came from documentation. Polars remained a capable alternative for analysts working primarily with Python transformations. The lab also considered an external weather benchmark and solicited model-assisted reviews. Those are contextual evidence and interpretations of the experiments. [Toolkit comparison in the historical record](polars-vs-duckdb.md) · [Review and corrections](../../evidence/reports/lab_formats_peer_review.md)

## Why PPDS has a toolkit

Selecting DuckDB settled how to execute a query. A user still had to know which resource to open on Zenodo, how to join a trial to its readings, and how to turn sparse rows back into the measured quantity. A trial with silent sensors still has the full number of recorded frames and a 353 × 64 platform. Inferring shape from the largest observed coordinate can drop empty rows, columns or frames. That is a scientific reason to maintain one tested reconstruction routine across notebooks.

| Public interface | Responsibility | A check that defines success |
|---|---|---|
| Direct files and SQL | Document resources, keys and units so independent readers can select and join physical tables. | A query using release keys reproduces the selected trial and its observations. |
| Shared package, `reader_data` | Open a release descriptor locally, over HTTP or by Zenodo record. Resolve named resources, expose Parquet tables to DuckDB, and open binary resources. | A generic fixture with different table names resolves the same values after download and through the supported hosted layout. |
| Dataset package, `ppds` | Apply PPDS conventions. Select a trial, reconstruct pressure in kPa with axes `(frame, y, x)`, or decode a mesh into vertices in metres and triangle indices. | Compare shape, calibrated values and zero-filled cells with a reference recording. Check a missing trial and distinguish it from a valid empty table selection. |
| marimo notebooks | Show analyses and playback using those interfaces. | A documented selection opens via the chosen release and the example shows interpretable results and units. |

The internal layout proposal assigned local and Zenodo resource access to a shared reader and assigned pressure physics to PPDS. The tagged implementation gives concrete evidence for that boundary. Its tests exercise named tables, flat filenames, sparse pressure reconstruction, missing trials and HTTP selection. The benchmark did not measure development cost or compare a toolkit against examples alone. The [toolkit decision standard](../../guide/toolkit-decision.md) turns this case into a proposed process for future projects. ## What shipped

PPDS dataset v1.0.0 stored participant descriptors on the trial table, published tabular resources as Parquet and shipped 190 STL members in `scans.zip`. Embedding STL bytes in each candidate encoding served the controlled benchmark. The ZIP keeps individual meshes accessible to ordinary tools. The release guide supplies its manifest and dictionary. Use it when reproducing a published analysis, and the archived fixture descriptions when interpreting benchmark measurements.
